# 03 · RAG 检索增强生成

> 核心考点：RAG 流程、Chunking 策略、向量检索、Rerank、评估指标、GraphRAG

---

### Q1 【基础】RAG 的完整流程是什么？为什么需要 RAG？

- **答案要点**：
  1. 完整流程：(a) 文档加载与解析（PDF/Word/HTML → 纯文本）；(b) Chunking 分块；(c) Embedding 向量化；(d) 存入向量数据库；(e) 检索：用户 query 向量化，相似度搜索取 Top-K；(f) 重排序 Rerank；(g) 拼接 prompt 送 LLM 生成回答。
  2. 为什么需要 RAG：(a) 大模型知识有截止日期，无法获取最新信息；(b) 模型参数记忆的知识有限，企业内部知识不在训练集中；(c) 纯靠微调注入知识成本高、容易遗忘；(d) RAG 可以引用来源，可溯源、可审计。
- **追问点**：
  - RAG 和微调的区别？（答：RAG 是外挂知识，实时更新、可溯源；微调是把知识压缩进参数，更新成本高；二者不互斥，实际项目经常一起用）
  - RAG 适合什么场景？（答：知识库问答、客服、企业内部文档查询、需要引用来源的场景；不适合需要深度推理和创造力的场景）

### Q2 【基础】常见的 Chunking 策略有哪些？怎么选 chunk size？

- **答案要点**：
  1. 固定长度分块：按 token 数硬切，最简单；缺点是可能切断句子/段落语义。
  2. 递归分块（RecursiveCharacterTextSplitter）：先按段落切，太大再按句子切，尽量保持语义完整；LangChain 默认方案。
  3. 语义分块（Semantic Chunking）：用 embedding 相似度判断语义边界，语义突变的地方切分；效果好但成本高。
  4. 结构化分块：按文档结构（标题、章节、表格）切分，保留层级信息；适合技术文档、法律文档。
  5. chunk size 选择经验：常用 256~1024 token；太小会上下文不完整，太大引入噪声、降低检索精度；overlap 一般设为 chunk size 的 10%~20%。
- **追问点**：
  - 为什么需要 overlap？（答：避免正好切在两个相关句子中间，导致两边都丢失上下文；overlap 让相邻 chunk 有重叠信息，保证检索到任一块都有完整语义）
  - 表格和图片怎么处理？（答：表格转 Markdown/HTML 文本再 embedding；图片用多模态模型生成描述文本）

### Q3 【进阶】向量检索和 BM25 关键词检索的区别？为什么常做混合检索？

- **答案要点**：
  1. 向量检索：基于语义相似度（cosine similarity），能理解同义词、相关概念；但对精确关键词（如专有名词、型号、代码）匹配不如 BM25。
  2. BM25：基于词频统计的稀疏检索，精确关键词匹配强；但无法理解语义（"手机"和"移动电话" BM25 认为不相关）。
  3. 混合检索：同时跑向量检索和 BM25，用 RRF（Reciprocal Rank Fusion）或加权融合两路结果；兼顾语义匹配和精确关键词匹配，实际效果显著优于单路。
  4. 重排阶段再用 cross-encoder 精排，进一步提升精度。
- **追问点**：
  - RRF 融合公式？（答：score = Σ 1/(k + rank_i)，k 常取 60；不需要归一化两路分数，直接按排名融合）
  - 向量检索用什么向量数据库？（答：Milvus、Qdrant、Weaviate、PGVector、Faiss；小规模用 Faiss/PGVector，大规模生产用 Milvus/Qdrant）

### Q4 【进阶】Rerank 重排序的作用是什么？常用模型有哪些？

- **答案要点**：
  1. 为什么需要 Rerank：向量检索是双塔（bi-encoder）结构，query 和 doc 独立编码，速度快但精度有限；Rerank 用 cross-encoder 把 query 和 doc 拼在一起输入模型，交互更充分，精度更高但慢，所以只对 Top-K 候选做精排。
  2. 典型流程：向量检索 Top-50 → Rerank 精排 Top-5 → 送 LLM。
  3. 常用 Rerank 模型：bge-reranker 系列（中文效果好）、Cohere Rerank、mxbai-rerank、cross-encoder/ms-marco。
  4. 效果提升：加 Rerank 后召回准确率通常能提升 10%~30%，是 RAG 系统最值得加的组件之一。
- **追问点**：
  - Rerank 为什么比向量检索准？（答：cross-encoder 中 query 和 doc 的每一个 token 都能互相注意，做深度语义交互；bi-encoder 各自编码完就比相似度，信息损失大）
  - Rerank 延迟会不会很大？（答：会，但只对 50 个候选做排序，每个候选几十毫秒，总延迟几百 ms，可接受）

### Q5 【进阶】RAG 系统的评估指标有哪些？

- **答案要点**：
  1. 检索阶段指标：(a) Recall@K（正确文档是否在前 K 个里）；(b) Precision@K；(c) MRR（平均倒数排名）；(d) NDCG。
  2. 生成阶段指标：(a) 忠实度（Faithfulness）：回答是否完全基于检索到的上下文，不编造；(b) 答案相关性：回答是否切题；(c) 上下文精度：检索到的上下文中有多少是有用的。
  3. 评估方法：(a) 人工评估（金标准）；(b) LLM-as-Judge（用 GPT-4 打分）；(c) 自动化指标如 RAGAS 框架。
  4. 端到端评估：构造一个问答对测试集，包含问题、标准答案、相关文档；跑完整 RAG 流程后对比。
- **追问点**：
  - RAGAS 是什么？（答：一个开源 RAG 评估框架，自动化计算 faithfulness、answer relevancy、context precision/recall 等指标）
  - 怎么构建评估测试集？（答：从真实业务问题中采样 100~500 条，人工标注标准答案和相关文档；定期回归测试）

### Q6 【实战】RAG 检索不到正确文档，你怎么排查和优化？

- **答案要点**：
  1. 先定位问题：是 query 理解问题还是索引问题？拿具体 case 手工查向量库看 Top-20 结果。
  2. 优化检索：(a) 加 Query Rewriting：让 LLM 把用户口语化问题改写成更适合检索的关键词；(b) 加 HyDE：先让模型生成一个假设答案，用这个假设答案去检索（假设答案的向量空间更接近真实文档）；(c) 混合检索（向量+BM25）；(d) 调优 chunk size 和 overlap。
  3. 优化 embedding：换更强的 embedding 模型（如 bge-m3、gte-large）；领域内做 embedding 微调。
  4. 优化索引结构：父子分块（小 chunk 检索、大 chunk 送 LLM）；加元数据过滤。
- **追问点**：
  - HyDE 的原理？（答：用户问题和文档的表达方式可能差异很大（用户说"怎么报销"，文档写"费用报销管理制度"）；先让 LLM 生成一个假设性回答，这个回答的语言风格更接近文档，用它去检索命中率更高）
  - Query Rewriting 适合什么场景？（答：用户问题口语化、有歧义、包含指代时特别有效）

### Q7 【实战】RAG 检索到了正确文档，但模型不引用/不基于它回答，怎么办？

- **答案要点**：
  1. Prompt 层面：明确要求"只根据提供的上下文回答，如果上下文里没有答案就说不知道"；给出 few-shot 示例展示正确引用方式。
  2. 上下文编排：把最相关的文档放在 prompt 开头和结尾（Lost in the Middle 效应：中间部分容易被忽略）；控制送入文档数量（3~5 篇为宜，太多反而干扰）。
  3. 训练层面：如果是自有模型，在 SFT 数据中加入 RAG 格式的样本，让模型学会"看到上下文就引用上下文"。
  4. 后处理：输出后用 NLI 模型校验回答是否和上下文矛盾；加引用标注要求。
- **追问点**：
  - Lost in the Middle 是什么？（答：研究发现模型对 prompt 开头和结尾的信息关注多，中间的信息容易被忽略；所以重要文档要放两头）
  - 为什么送太多文档反而效果差？（答：上下文太长会稀释相关信息，模型注意力分散；且长上下文下模型的"服从性"会下降）

### Q8 【进阶】GraphRAG 和传统向量 RAG 的区别？

- **答案要点**：
  1. 传统向量 RAG：扁平的 chunk 向量检索，适合单点事实查询（"XX 的地址是多少"）；但不擅长全局性问题（"整个项目的主要风险有哪些"）。
  2. GraphRAG：先从文档中提取实体和关系构建知识图谱；对全局问题，先在图谱上做社区检测，生成社区摘要，回答时汇总相关社区信息。
  3. 优势：(a) 擅长全局性、总结性问题；(b) 可以做多跳推理（A→B→C 关系链）；(c) 实体关系清晰可解释。
  4. 劣势：构建图谱成本高（实体抽取、关系抽取都要 LLM）；更新维护复杂；单点事实查询效率不如向量 RAG。
- **追问点**：
  - GraphRAG 适合什么场景？（答：大量文档的全局分析、关系密集型领域（如法律案件、企业组织架构、投资关系））
  - 微软的 GraphRAG 是怎么做的？（答：先用 LLM 从文档中抽取实体关系建图，然后做层次化社区检测，每个社区生成摘要；全局查询时 map-reduce 各社区摘要）

### Q9 【实战】企业级 RAG 中，多租户和数据权限隔离怎么设计？

- **答案要点**：
  1. 向量数据库层面：每个租户单独 collection/index（物理隔离），或者共享 index 但加 tenant_id 元数据过滤（逻辑隔离）。
  2. 检索时：在 query 向量搜索后，强制加 tenant_id 过滤条件；确保不会跨租户检索到文档。
  3. 文档权限：更细粒度的文档级 ACL——用户只能检索到自己有权限的文档；用元数据存储文档权限，检索时联合过滤。
  4. 生成时：prompt 中绝不加入跨租户信息；输出侧做敏感信息检测。
- **追问点**：
  - 物理隔离 vs 逻辑隔离怎么选？（答：小租户多用逻辑隔离（省资源），大客户/合规要求高的用物理隔离（独立 collection））
  - 检索时加过滤会不会影响召回？（答：会，因为过滤后向量空间变小；需要在 embedding 时就考虑权限维度，或者用混合检索+权限过滤）

### Q10 【进阶】RAG 系统上线后，效果不好怎么系统性优化？

- **答案要点**：
  1. 建评估集：先有 100~500 条标准问答对，每次优化都跑回归，量化提升。
  2. 分层排查：检索准确率多少？生成忠实度多少？先找短板。
  3. 数据层：文档清洗质量、chunking 策略、embedding 模型选型。
  4. 检索层：混合检索、Rerank、Query 改写、父子分块。
  5. 生成层：Prompt 优化、上下文编排、模型选型。
  6. 闭环：收集 bad case，定期迭代优化。
- **追问点**：
  - 最常见的问题是哪一层？（答：检索层问题占 70% 以上，大部分 RAG 效果差都是因为检索不到正确文档，而不是 LLM 不会回答）
