# 06 · Agent 与工具调用

> 核心考点：ReAct、Function Calling、多智能体、记忆系统、工具检索

---

### Q1 【基础】什么是 Function Calling？和传统的工具调用有什么区别？

- **答案要点**：
  1. 定义：让大模型根据用户意图，自动决定调用哪个外部工具（API）、生成正确的参数，然后把工具返回的结果整合进回答。
  2. 传统工具调用：需要人工写 if-else 规则判断什么时候调什么工具，硬编码；扩展性差。
  3. Function Calling：模型理解自然语言意图，自动选择工具、生成参数；由模型做"决策层"，工具做"执行层"。
  4. 流程：用户提问 → 模型判断需要调工具 → 输出工具名+参数（结构化 JSON）→ 系统执行工具 → 结果喂回模型 → 模型生成最终回答。
- **追问点**：
  - Function Calling 是怎么训练出来的？（答：在 SFT 数据中加入"调用工具"格式的样本，让模型学会输出结构化的工具调用 JSON；推理时通过 prompt 描述有哪些可用工具）
  - 模型怎么知道有哪些工具可用？（答：在 system prompt 中列出每个工具的名称、描述、参数 schema；模型根据描述判断该不该用、用哪个）

### Q2 【基础】ReAct 框架的核心思想是什么？

- **答案要点**：
  1. ReAct = Reasoning + Acting，让模型交替进行"思考（Thought）"和"行动（Action）"：
     - Thought：分析当前状态，决定下一步做什么。
     - Action：调用工具执行具体操作。
     - Observation：工具返回结果，模型观察并继续思考。
  2. 循环直到模型判断可以给出最终答案（Final Answer）。
  3. 优势：(a) 把推理和工具调用结合起来，模型可以边想边做；(b) 过程可解释，每一步都有 Thought 记录；(c) 可以处理需要多步推理的复杂任务。
- **追问点**：
  - ReAct 和 Chain-of-Thought 的区别？（答：CoT 只在"脑内"推理，不调用外部工具；ReAct 是推理+行动交替，可以和外部世界交互）
  - ReAct 的局限？（答：步数多了容易跑偏、陷入循环；Thought 质量依赖模型本身能力）

### Q3 【进阶】多智能体系统（Multi-Agent）有哪些典型架构？

- **答案要点**：
  1. 主管-工人（Manager-Worker）：一个主管 Agent 拆解任务，分配给多个工人 Agent 执行，主管汇总结果。
  2. 辩论/协作（Debate/Collaboration）：多个 Agent 从不同角度讨论同一个问题，互相 critique，最终收敛到更好的答案。
  3. 流水线（Pipeline）：不同 Agent 各司其职，如：研究员→分析师→撰稿人→审校，像工厂流水线。
  4. 角色分工：如 AutoGen 的 AssistantAgent + UserProxyAgent，模拟人和 AI 的对话协作。
  5. 适用场景：复杂任务拆解、需要多视角、任务有明确阶段划分。
- **追问点**：
  - 多 Agent 一定比单 Agent 好吗？（答：不一定——简单任务单 Agent 就够；多 Agent 增加复杂度和成本，还可能引入沟通错误；只有任务确实需要分工时才值得）
  - 多 Agent 系统最大的工程挑战？（答：上下文管理——每个 Agent 都有自己的上下文，跨 Agent 传递信息需要精心设计，容易丢信息或累积噪声）

### Q4 【进阶】Agent 的记忆系统怎么设计？短期记忆和长期记忆？

- **答案要点**：
  1. 短期记忆：就是当前对话的上下文窗口；受上下文长度限制，超过就会被截断。
  2. 长期记忆：把重要信息存到外部数据库（向量库/键值库），需要时检索出来；类似 RAG 的思路。
  3. 记忆写入策略：不是所有信息都存——要判断什么值得记（用户偏好、历史决策、重要事实），避免记忆爆炸。
  4. 记忆检索：根据当前任务相关性，检索相关记忆注入上下文；类似 RAG 的检索-生成流程。
  5. 记忆管理：定期总结旧记忆、去重、遗忘过时信息。
- **追问点**：
  - 记忆和 RAG 的区别？（答：技术上很像——都是向量检索；区别在于 RAG 检索的是"知识文档"，Agent 记忆检索的是"和这个用户/任务相关的历史信息"）

### Q5 【实战】Function Calling 经常格式不对/参数错，怎么办？

- **答案要点**：
  1. Prompt 层面：明确给出工具参数的 JSON Schema 描述；给 few-shot 示例展示正确的调用格式。
  2. 格式约束：用 JSON mode / structured output 强制模型输出合法 JSON；用 grammar 约束（如 Outlines、XGrammar）保证 schema 正确。
  3. 重试机制：解析失败时把错误信息喂回模型，让它修正后重试。
  4. 微调：如果是自有模型，在 SFT 数据中加入大量 Function Calling 样本，让模型学会稳定输出格式。
  5. 工具设计：参数尽量简单，必填参数少一点；枚举值给清楚，减少模型"自由发挥"的空间。
- **追问点**：
  - 什么是 structured output？（答：让模型严格按照指定 JSON Schema 输出，语法层面保证合法，而不是靠 prompt 约束；vLLM/Grammar 等框架支持）

### Q6 【实战】Agent 循环失控（无限调用工具）怎么处理？

- **答案要点**：
  1. 最大步数限制：设置 max_steps（如 10 步），超过就强制停止并返回当前最佳结果。
  2. 重复检测：检测连续多次调用同一工具+相同参数，发现重复就中断。
  3. 超时机制：单步超时 + 总超时。
  4. 中间检查点：每隔几步让模型做一次"是否已经可以回答"的判断。
  5. Prompt 引导：在 system prompt 中明确告诉模型"最多调用 N 次工具，之后必须给出答案"。
- **追问点**：
  - 为什么会无限循环？（答：模型陷入"想调工具→工具结果不好→再调→还是不好"的死循环；或者模型不会判断什么时候该停下来）

### Q7 【进阶】Tool Retrieval（工具检索）为什么需要？什么时候需要？

- **答案要点**：
  1. 为什么需要：当可用工具数量很多（几十上百个）时，全部塞进 prompt 会占用大量 token，而且模型注意力分散、选错工具。
  2. Tool Retrieval 思路：先把所有工具的描述做 embedding 存起来；用户提问时先检索 Top-K 最相关的工具，只把这 K 个工具塞进 prompt。
  3. 适用场景：工具数量 > 20~30 个；工具描述很长；不同场景下可用工具集不同。
  4. 类似 RAG：工具库就是"知识库"，用户 query 就是检索输入，检索后拿到相关工具描述。
- **追问点**：
  - 工具检索会不会漏？（答：会，检索不到正确工具模型就用不了；所以要在召回率和 prompt 长度之间做 trade-off；一般 Top-5~10 够用）

### Q8 【实战】怎么评估一个 Agent 系统的好坏？

- **答案要点**：
  1. 任务成功率：端到端任务完成的比例（最核心指标）。
  2. 工具调用准确率：选对工具的比例、参数正确率。
  3. 步数效率：完成任务用了多少步，越少越好。
  4. 人工评估：看最终回答质量、过程合理性。
  5. 基准测试：用公开 Agent benchmark 如 SWE-bench、WebArena、GAIA 等。
  6. 线上指标：用户满意度、重试率、人工接管率。
- **追问点**：
  - 为什么 Agent 评估比普通 LLM 评估难？（答：Agent 有长链路、多步决策，单步对不代表端到端对；需要看最终结果而非中间步骤）

### Q9 【进阶】AutoGPT 类自主 Agent 和 Claude/GPT 类对话 Agent 有什么本质区别？

- **答案要点**：
  1. AutoGPT 类：给一个目标，Agent 自己拆解、自己执行、自己迭代，长时间自主运行；目标导向，中间不需要人干预。
  2. 对话 Agent：每一步都需要用户输入驱动；是"助手"角色，人在环里（human-in-the-loop）。
  3. 本质区别：自主性（autonomy）程度不同。AutoGPT 追求高自主，但实际效果经常跑偏；对话 Agent 低自主但可控、可靠。
  4. 当前趋势：业界更偏向"人在环中"的 Agent——Agent 提建议、执行，人确认关键决策；完全自主的 Agent 在生产环境风险太大。
- **追问点**：
  - 完全自主 Agent 为什么难落地？（答：错误会累积——一步错步步错；没有人类纠正的话，小偏差会滚成大问题；且边界情况太多，模型很难覆盖）

### Q10 【实战】设计一个「订机票 Agent」，你会怎么拆？

- **答案要点**：
  1. 工具清单：搜索航班、查询价格、预订机票、取消订单、查用户信息。
  2. 流程：
     - (a) 理解用户需求：出发地、目的地、日期、人数、舱位。
     - (b) 信息不全时主动追问（ReAct 模式）。
     - (c) 调用搜索航班工具，拿到候选结果。
     - (d) 展示选项让用户选择。
     - (e) 确认后调用预订工具，返回订单信息。
  3. 安全设计：预订前必须用户确认；金额、日期等关键信息要显式复述确认。
  4. 边界处理：无航班结果怎么办？多轮上下文怎么保留？
- **追问点**：
  - 怎么处理多轮对话中的指代？（如"那第二天的呢"——需要结合上下文理解"第二天"指的是哪天）
